# ES256 tokens

`knos_oidc` verifies RS256 tokens by doing the RSA arithmetic itself, over several transactions. An ES256 token
(ECDSA on P-256 with SHA-256) is verified another way: Solana checks the signature in an instruction of its own, and
`VerifyEs256` checks that what Solana verified is the issuer's key, the token and its signature. One transaction.

**Status: implemented and tested here; not deployed.** The source is `programs-v2/knos_oidc/src/es256.rs`; the tests
are `programs-v2/handlers/tests/knos_oidc_es256.rs` (the built program in LiteSVM, with its secp256r1 precompile) and
`tests/test_es256.py`. No public program id runs it. It ships in the next `knos_oidc` build that is proposed, together
with the strict JSON reader (see "What the release run does" at the end). Every number below is measured by those
tests on 2026-10-06 or carries a link.

## What Solana provides: the secp256r1 precompile

[SIMD-0075](https://github.com/solana-foundation/solana-improvement-documents/blob/main/proposals/0075-precompile-for-secp256r1-sigverify.md)
adds the program `Secp256r1SigVerify1111111111111111111111111`. An instruction to it verifies up to 8 signatures,
"ECDSA using the NIST P-256 curve and the SHA-256 hashing algorithm"; if one does not verify, the transaction fails
and no program runs.

| Bytes of the instruction's data | What |
| --- | --- |
| 1 | the number of signatures, 1 to 8 |
| 1 | padding |
| 14 for each signature | seven little-endian `u16`: signature offset, signature instruction index, public key offset, public key instruction index, message offset, message length, message instruction index |
| the rest | whatever the offsets point at |

- The public key is 33 bytes, SEC1 compressed. The signature is 64 bytes: `r`, then `s`, 32 bytes each, big-endian.
- The precompile hashes the message itself (SHA-256), so the caller hands over the message, not a digest.
- An instruction index of `0xFFFF` means "this instruction"; any other value names another instruction of the same
  transaction. So the key, the signature and the message may each sit in a different instruction.
- "All data retrieved via offsets come from `instruction_data`": the message has to be in the transaction. It cannot be
  read from an account.
- Low S only: "the precompile must mitigate these attacks by enforcing the usage of `lowS` values, in which
  `s <= n/2`", and it "must immediately fail upon the detection of any signature that includes a `highS` value".

Where it runs. The precompile has been active on mainnet since June 2025
([Helius, "Solana passkeys"](https://www.helius.dev/blog/solana-passkeys): "In June 2025, Solana enabled native
on-chain verification of secp256r1 (P-256) signatures via a new precompile"). `knos_passkey` uses it on devnet
(`programs-v2/knos_passkey/src`), and LiteSVM 0.7.1, which the tests here run, includes it. We did not find the
activation epoch of each cluster in a primary source; the release run's rehearsal on devnet is the check that counts.

## The size limit: the token rides in the transaction

Because the message must be instruction data, the whole signing input (`base64url(header) "." base64url(payload)`)
travels in the one transaction, beside the key, the signature and the offsets. A legacy or v0 transaction is at most
1,232 bytes.

| Part of the transaction (legacy format) | Bytes |
| --- | --- |
| one signature (the payer's), with its count | 65 |
| message header | 3 |
| seven account keys with their count: payer, token account, key account, system program, instructions sysvar, the precompile, `knos_oidc` | 225 |
| recent blockhash | 32 |
| instruction count | 1 |
| the precompile instruction without the message: program index, no accounts, data length (2), count and padding (2), offsets (14), key (33), signature (64) | 117 |
| `VerifyEs256`: program index, five account indexes with their count, data length, one byte of data | 9 |
| **everything but the signing input** | **452** |
| **the signing input, at most** | **780** |

**The largest ES256 token that fits is one whose signing input is 780 bytes** (867 characters as a compact token with
its signature). `the_largest_token_fills_a_legacy_transaction` builds that transaction, measures exactly 1,232 bytes,
verifies it, and measures 1,233 for a signing input of 781. The 780 leaves no room for anything else: a priority fee
instruction (the Compute Budget program's key, 32 bytes, and a 12-byte instruction) takes 44, which leaves 736. None is
needed for compute: see the measurements below.

What that means in practice. The fixed test token (five claims: `iss`, `sub`, `aud`, `exp`, `iat`) has a signing
input of 218 bytes. A token shaped like a SPIFFE JWT-SVID (a 32-character `kid`, an `aud` list of one, `exp`, `iat`,
a `sub` of 40 characters) comes to 272 bytes when built with `tests/_es256.py`. A token with as many claims as GitHub
Actions' (about 2,100 bytes, RS256, [OIDC.md](OIDC.md)) would not fit. **So ES256 as built here covers small workload
tokens, and refuses a large one by not fitting, before any program runs.** The RS256 path has no such limit (8,192
bytes) because the program reads that token from an account.

### Larger transactions

[solana.com/upgrades/larger-transaction-sizes](https://solana.com/upgrades/larger-transaction-sizes), read on
2026-10-06, says: "The maximum transaction size is now 4096 bytes, up from 1232", "the larger size is only available
in the `v1` transaction format, specified in SIMD-0385", legacy and v0 transactions keep the 1,232-byte limit, and
"the `txv1` feature gate activated at the start of mainnet epoch 1035 on September 15, 2026", with testnet and devnet
active before it. The proposal's own text,
[SIMD-0296](https://github.com/solana-foundation/solana-improvement-documents/blob/main/proposals/0296-larger-transactions.md),
still showed the status "Review" on the same day.

What it would change here: nothing in the program. `VerifyEs256` reads the precompile's instruction through the
instructions sysvar and never looks at the transaction's format, and its own cap is the token account's (8,192
bytes). A v1 transaction would carry a signing input of roughly 3,600 bytes; that figure is an estimate, not a
measurement. **Nothing here has built, sent or measured a v1 transaction**: the Rust crates of this tree are the
2.2 line (the page asks for 4.2 or later), and a v1 transaction must set its compute unit limit and its loaded
accounts size itself or it cannot run. Until the rehearsal has sent one on devnet, the bound is 780.

## The signature: JWS writes `r || s`, the precompile wants the lower `s`

[RFC 7518, section 3.4](https://www.rfc-editor.org/rfc/rfc7518.html#section-3.4): "Turn R and S into octet sequences
in big-endian order, with each array being 32 octets long", "concatenate the two octet sequences in the order R and
then S", and "the resulting 64-octet sequence is the JWS Signature value". That is byte for byte what the precompile
takes, so no DER decoding is needed: the relayer base64url-decodes the third part of the token and has the 64 bytes.

The RFC says nothing about which `s`. For every valid ECDSA signature `(r, s)`, `(r, n - s)` is valid too (`n` is the
order of the curve), and a signing library may write either. The precompile refuses the upper one. So **the relayer
replaces `s` by `n - s` when `s > n/2`** (`normalise` in `tests/_es256.py`).

Why that is safe:

- It needs no secret. Anyone holding the token can compute `n - s`; an attacker gains nothing a bystander lacks.
- It changes nothing that was signed. The header and the payload are untouched; the precompile verifies the issuer's
  key over the same signing input. The claims a consumer reads are the ones the issuer signed.
- It removes the second spelling instead of adding one. A consumer names its single-use marker by the signature
  (`knos_pay`: `["used", sha256(signature)]`). If both spellings verified, one token would have two markers. With
  only the lower `s` accepted, one token has one accepted signature. `VerifyEs256` checks `s <= n/2` again itself
  (error 83) rather than rest that property on the precompile alone.
- The token account holds the signature that was verified (the lower spelling, as unpadded base64url). For a token
  whose issuer wrote the upper `s`, the stored third part therefore differs from the issuer's text by exactly that
  substitution. A reader who compares the stored token with the issuer's original must normalise first.

`a_token_already_used_is_refused` sends the upper spelling of a good signature: the precompile refuses the
transaction.

## What `VerifyEs256` checks

Instruction 15, accounts `payer (signer, writable)`, `token (writable)`, `key`, `system program`, `instructions
sysvar`, no data. In order:

1. `key` is a P-256 key account of this program (137 bytes; its third byte is `0xEC`, which no RSA key, token or
   issuer account has there), usable now by the same rule as an RSA key: not revoked, past its delay, approved if it
   was attested, not expired.
2. The instruction **right before this one** is the secp256r1 precompile. Not anywhere else in the transaction, and
   not absent.
3. That instruction holds **exactly one** signature and all three instruction indexes are `0xFFFF`: the key, the
   signature and the message are in its own data, at offsets that lie inside it. A record that points at another
   instruction is refused, because the bytes this program would read at those offsets would not be the bytes the
   precompile verified.
4. The key it verified is the 33 bytes the key account holds.
5. `s <= n/2`.
6. The message is one signing input: two non-empty base64url parts and one dot. The header is one strict JSON
   object ([strict.rs](../programs-v2/knos_oidc/src/strict.rs)) whose `alg` is `"ES256"`.
7. The token account is `["tok", payer, sha256(signing input)]` and **does not exist yet**: one payer verifies one
   token once.
8. The payload is one strict JSON object; `iss` is the issuer the key was registered for; `exp` is a number at most
   a day ahead of the clock.

Then it writes the account the RS256 path writes, in the same layout and marked VERIFIED: issuer number, key account,
expiry, payload decoded in place, issuer hash and registrant, and the compact token with the verified signature. Two
bytes say which path wrote it (the count of squarings and the limb count are 0). `knos_oidc::verified`,
`issuer_hash`, `is_private` and `registrant`, which consumers link, read it unchanged; `claims.rs` is not touched.
`Close` closes it like any token account. The single-use marker is the consumer's, as for RS256: `knos_pay` creates
`["used", sha256(signature)]` when it spends a token, and reads the signature from this account.

Keys are admitted the way RSA keys of other issuers are, by instructions 10 to 14: an attested key
(`["eckey", sha256(url), sha256(key)]`, GitHub's signature over the audience
`knos-oidc:eckey:<sha256(url) hex>:<sha256(key) hex>`, a day's delay, the guardian's approval, 30 days until
refreshed) or a private key of one wallet (`["epkey", registrant, sha256(url), sha256(key)]`, marked private in every
token it verifies). The audience differs from an RSA key's, so an attestation of one kind never admits the other.
**No pinned workflow asks for the `eckey` audience today, so on a real build only private P-256 keys can be
registered until a rotate workflow that does is pinned.**

Not built: ES384, ES512, EdDSA, PS256; a token whose base64url parts carry `=` padding (the strict decoder refuses
it; AWS's load balancer writes its ES256 tokens that way, see below); a client command. The relayer in
`src/knos/settle/v2` does not send `VerifyEs256` yet.

`tests/fixtures/knos_oidc_v2_test.so`:

| Transaction (the precompile, then `VerifyEs256`) | Signing input | Transaction bytes | Compute units |
| --- | --- | --- | --- |
| the test token, a private key | 218 | 670 | 26,322 |
| the largest token, a private key | 780 | 1,232 | 41,644 |
| the test token, an attested key | 218 | 670 | 26,322 |

The precompile's own work is not charged to the transaction's compute units in LiteSVM, so the figures are
`VerifyEs256` and the account it creates. All are under the 200,000 units an instruction gets by default: no compute
budget instruction is needed. For comparison an RS256 token takes several `Step` transactions ([OIDC.md](OIDC.md)).

The RS256 path on the new build: every handler test of the four programs passes against it, and a short run of the
differential (`python tests/test_oidc_differential.py --cases 1020`, not recorded) gave 150 accepted by both, 870
refused by both, 0 disagreements. The recorded long run in `docs/fuzz.json` is this build's: the test build
`cd9d7d68…8eabf5` that `tests/fixtures/SHA256SUMS` gives, 8,855 cases, 0 disagreements.

What the tests refuse, each with the program untouched afterwards: a signature by another key (under the registered
key, and under its own); an altered payload; a signature made for another message; no precompile instruction; the
precompile at another index (after, or two before); offsets that send the precompile to another instruction's data
for the signature, the key or the message; two signatures in one precompile instruction; `alg` that is not ES256, or
named twice; a token of another issuer; an expiry too far ahead; a token already verified; the upper `s`; an RSA key
account given to `VerifyEs256`; a P-256 key account given to `Step`, `Approve`, `Revoke` or `KeyParams`; an RSA
attestation used to register a P-256 key.

## Who signs ES256

- **SPIFFE / SPIRE.** A JWT-SVID's `alg` is one of RS256, RS384, RS512, ES256, ES384, ES512, PS256, PS384, PS512
  ([JWT-SVID, section 2.1](https://github.com/spiffe/spiffe/blob/main/standards/JWT-SVID.md)), and SPIRE's server signs
  with `ec-p256` unless told otherwise ([SPIRE server configuration](https://spiffe.io/docs/latest/deploying/spire_server/):
  `ca_key_type` defaults to `ec-p256`, `jwt_key_type` to "the value of ca_key_type or ec-p256 if not defined"). `sub`,
  `aud` and `exp` are required. Small tokens: the shape measured above is 272 bytes.
- **Supabase Auth.** Offers ES256, RS256, EdDSA and HS256 signing keys and recommends P-256
  ([Supabase, JWT signing keys](https://supabase.com/docs/guides/auth/signing-keys)). Size not measured here.
- **Kubernetes service accounts.** RS256 on the managed clusters we looked at; a cluster with an ECDSA signing key
  signs ES256, ES384 or ES512 ([VERIFIER.md](VERIFIER.md)).
- **AWS Application Load Balancer.** "An Application Load Balancer uses ES256 (ECDSA using P-256 and SHA256) to
  generate the JWT signature", and its token "includes padding characters at the end"
  ([AWS documentation](https://docs.aws.amazon.com/elasticloadbalancing/latest/application/listener-authenticate-users.html)).
  The padding is part of what is signed, and the strict decoder refuses it: **not verified by this build.**
- **Not ES256:** GitHub Actions and GitLab CI sign RS256. AWS's outbound identity federation recommends ES384
  ([VERIFIER.md](VERIFIER.md)), which no Solana precompile verifies.

No token of any of these issuers has been verified by this code: the tests use two fixed test keys.

## What the release run does

1. Build `knos_oidc` once, verified (`solana-verify build`), from a commit that holds both the strict JSON reader
   and this module: one build, one hash, one proposal. The strict JSON build that is in the tree and not yet
   proposed is superseded by it.
2. The program grows by about 32,000 bytes, and it fits where it is: the verifier's program data account on devnet
   has room for 279,360 bytes (asked of devnet on 2026-10-05, [ASSURANCE.md](ASSURANCE.md)) and the real build is
   202,032. No extension is needed, so ES256 is in the default build and behind no feature. If a later build
   outgrows the account, `scripts/deploy_v2.sh --propose` extends it first (`ExtendProgram`, which anyone may send
   while the cluster has not activated `ExtendProgramChecked`: devnet listed it inactive on 2026-10-04); once that
   is active only the upgrade vault can extend, by a proposal of the multisig that the script does not make.
3. Rehearse on a staging program id on devnet: register a private P-256 key, send the precompile and `VerifyEs256`
   in one legacy transaction, read the token account back, send a signing input of 780 bytes and one of 781, send a
   token whose signature has the upper `s` raw (refused) and normalised (accepted), and verify the same token a
   second time (refused). Then, if v1 transactions are wanted, send one above 1,232 bytes and record its size.
4. Run the long differential again against the new test build and record it (`python
   tests/test_oidc_differential.py --cases N --record` rewrites `docs/fuzz.json`; done on 2026-10-06: `docs/fuzz.json`,
   `docs/ASSURANCE.md`, `docs/load.json` and `docs/LOAD.md` name the new test build `cd9d7d68…8eabf5`).
5. Propose the upgrade of the public `knos_oidc` id. Until it executes, ES256 is "tested", not "deployed".
