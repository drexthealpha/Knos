# x402 "knos-order": money released by a signature, not before delivery

**What only a chain does here:** the buyer's money sits in an account no person and no company holds a key to, and
a program releases it on one thing: a third party's signature that the work was accepted. There is no payment company
in the middle and no oracle reporting what happened: the program checks the signature itself. Without the signature
the money goes back to the buyer at the deadline, and nobody can stop that either.

**This is a proposal. It is not part of x402**, it is not registered with the x402 Foundation, and no facilitator
other than the resource server itself implements it. It is written so that someone could. It runs on Solana devnet
with test USDC, the programs are upgradeable through a multisig and have had no outside audit.

Every agent payment rail read for this page moves money before or at delivery, or leaves the decision with the
seller. None checks that the work was accepted. How much x402 carries, by its own count:
[x402.org](https://www.x402.org) showed, for the last 30 days, 75.41M transactions, $24.24M of volume, 94.06K buyers
and 22K sellers when it was fetched on 6 October 2026. That is the figure used here, because anyone can open the
page and check it; larger cumulative figures quoted elsewhere are not. None of that volume is Knos's: `knos-order`
has moved test USDC on devnet only.

[`examples/agent_pays_agent`](../examples/agent_pays_agent) shows the whole thing with two agents: one finds a task
and funds the order, the other delivers, an evaluator accepts and the program pays; then the same with wrong work,
where nothing is released and the buyer is refunded at expiry.

## What is missing in x402 today

x402 lets a server answer `402 Payment Required` with a machine-readable price, and a client pay and ask again. A
*scheme* says how the payment is authorised and settled. The schemes the specification repository defines move money
at or before delivery, or leave the decision with the seller: `exact` transfers a fixed amount, `upto` a metered
one, `batch-settlement` settles a channel, and `auth-capture` holds the money until the resource server captures,
voids or refunds it
([x402 specification v2](https://github.com/x402-foundation/x402/blob/main/specs/x402-specification-v2.md), and the
schemes under `specs/schemes`, read on 6 October 2026). None conditions the payment on the thing delivered being
accepted by someone who is neither the buyer nor the seller. For an API call
that is right: the response is the delivery. For work (a fix, a build, a review) it is not: the buyer pays for a
result, and the result is judged after the response.

## The scheme

`knos-order` makes the payment requirement a **Knos work order**: an escrow on Solana that pays when GitHub signs
that the order's terms were met, and returns the money to its funder if nobody delivers.

1. The client asks for the resource. It may name its wallet in an `Attested-Payer` header.
2. The server answers `402` with one `accepts` entry of scheme `knos-order`. It names the order to fund: the program,
   the order's address (when the client named its wallet; otherwise `null` and the client derives it), the terms
   and their hash, the amount, the mint, the fee the funder pays on top, and the workflows whose signed run is the
   judge.
3. The client checks the requirement against its own limits, derives the order's address itself, and funds the
   order with `knos_pay`'s `FundOrderWallet`. Its money is now in the order's own token account. Nobody holds a key
   to it.
4. The client asks again with `PAYMENT-SIGNATURE`: the order's address is the payment proof.
5. The server reads the order from the chain (it is `knos_pay`'s, for this issue, these terms, this amount, these
   workflows, open, with time left) and delivers. Its `PAYMENT-RESPONSE` says `escrowed`: the seller has not been
   paid yet.
6. **The seller is paid when the acceptance lands**: the order's pinned workflow runs, GitHub signs a token that
   names the order and the payee, `knos-oidc` verifies the signature on chain and `PayOrder` pays the payee the
   amount whole. If that never happens, anyone sends `RefundOrder` after the deadline and the amount and the fee
   return to the client.

Headers and objects are x402 v2's: `PAYMENT-REQUIRED`, `PAYMENT-SIGNATURE` and `PAYMENT-RESPONSE`, each the base64 of
the JSON below ([HTTP transport v2](https://github.com/x402-foundation/x402/blob/main/specs/transports-v2/http.md)). The
only new header is `Attested-Payer` on the first request, and it is optional.

The name follows the specification's own: a scheme is a lower-case word in `accepts[].scheme` (`exact`, `upto`,
`auth-capture`, `batch-settlement`), specified per network family in `specs/schemes/<scheme>/scheme_<scheme>_<family>.md`; this page
is what `specs/schemes/knos-order/scheme_knos_order_svm.md` would hold. What is not a payment field travels as an
extension, which the specification defines as `{ info, schema }` under a key of `extensions`: the key here is
`knos-order`, `schema` is the JSON Schema of `info`, and a client that does not know the extension ignores it. A
server can offer `exact` beside it in the same `accepts` list: a client that knows only `exact` pays before delivery
as it does today.

| x402 field | in `knos-order` |
|---|---|
| `scheme` | `"knos-order"` |
| `network` | the cluster, as x402 names it (`solana:EtWTRABZaYq6iMfeYKouRu166VU2xqa1` is devnet) |
| `amount` | what the payees receive, in the mint's smallest units. The funder pays `extra.fee` on top |
| `asset` | the mint |
| `payTo` | the seller's wallet. The escrow pays it, not the client; the judge's token names the payee |
| `maxTimeoutSeconds` | the order's work time: after it, an unpaid order can be refunded |
| `extra.program` | `knos_pay`'s address on that cluster |
| `extra.order` | the order's address for the named payer, or `null` |
| `extra.repoId`, `extra.issue`, `extra.seq` | what the order is for: its scope is `sha256("knos3:scope" || repoId || issue)` and its address `["ord", scope, payer, seq]` |
| `extra.terms`, `extra.termsHash`, `extra.mode` | the acceptance terms (a JSON document), their sha256, and how they are judged |
| `extra.workflows` | the repository and commit of the workflows whose GitHub-signed run pays the order |
| `extra.fee` | `knos_pay`'s fee for this amount, paid by the funder on top, by the rule of the build that is live: 0.30% of the amount, at least 0.05, from knos_pay 2.2 on; 2.5% of the first 1,000, 1% to 50,000, 0.5% above, at least 0.40, until that upgrade executes. The server asks the program which build it is (Version, simulated); a client that did not ask accepts the fee of either rule and nothing else. Orders funded before the upgrade keep the rate fixed at their funding. The messages below were recorded on this tree's build, knos_pay 2.2: their fee is 0.06 on 20.00. The public program, knos_pay 2.1 until the 2.2 upgrade executes, charges 0.50 on the same 20.00 |
| `extra.payee.githubId` | who the seller is to the judge |

## What each side must check

The client, before it signs: the program is one it knows; the mint and the amount are within its limits;
`termsHash` is the hash of `terms`; `fee` is the program's fee for the amount; `extra.order`, when given, is the
address its own wallet's funding creates. The server, before it delivers: the account at `payload.order` is owned
by the program, is an Order whose own fields derive that address, is for this scope, mint, terms, mode and
workflows, holds at least the amount, is open, has enough time left, and has not paid for a delivery before.
Neither trusts the other's arithmetic, and neither can move the escrow.

## What it does not do

- It does not make delivery atomic. The server delivers against escrow and carries the risk that the acceptance
  never comes; the client carries the risk that the delivery is not what the terms describe, and is then refunded
  after the deadline, not before.
- The judge is GitHub-shaped: a workflow run whose token GitHub signs. An acceptance that no workflow can decide
  cannot be expressed.
- The public x402 facilitator is not involved, and whether its allow-list would take a program it does not know
  was not confirmed. The resource server verifies for itself.
- No facilitator but Knos's own example implements the scheme. It is proposed on the specification repository
  (issue #3720 and a draft pull request, #3731, with the specification only), and no maintainer has answered yet.
  What a facilitator would have to do is small and is written down below.
- Amounts are bounded by `knos_pay`: at least 5 and at most 100,000 whole units of the mint per order (the devnet
  build's cap).
- A small ticket is not an order of its own. Outcomes under 20 are netted into one release per payee per period, with
  the fee's floor once: [NETTING.md](NETTING.md).

## What a facilitator does in this scheme

Less than in any other: it signs nothing, pays no fee and can move no money. `/verify` reads the account at
`payload.order` and applies the server's checks above; `/settle` reads it again and answers `escrowed`. The escrow
program pays or refunds later, with no facilitator in the path.

The way a scheme is proposed there, as the repository's `CONTRIBUTING.md` and `specs/CONTRIBUTING.md` had it when
they were read again on 6 October 2026: open an issue or discussion with the problem, the approach and why the
existing schemes do not cover it; then a pull request with the specification only, as
`specs/schemes/<name>/scheme_<name>.md` from `scheme_template.md` and one `scheme_<name>_<network>.md` per network
from `scheme_impl_template.md`; code in one SDK after the specification is agreed. The repository
[x402.org](https://www.x402.org) links to is `x402-foundation/x402`. The two specification files for `knos-order`
are written in that shape and were proposed there on 7 October 2026:
[issue #3720](https://github.com/x402-foundation/x402/issues/3720) states the problem and the approach, and
[draft pull request #3731](https://github.com/x402-foundation/x402/pull/3731) adds the two specification files and
nothing else. Before the pull request was opened, `python scripts/upstream_check.py x402-foundation/x402` found a
pull request merged there that day (#3723), and its commits were made through GitHub, which signed them. No
maintainer has answered either yet, and no facilitator outside Knos implements the scheme: the count of outside
facilitators is 0.

## Two agents, end to end

[`examples/agent_pays_agent`](../examples/agent_pays_agent) is the scheme with nobody at the keyboard: a buyer
agent and a seller agent, each a script with a key of its own and no model call, and an evaluator that is neither.

| step | who | what happens | where the money is |
|---|---|---|---|
| 1 | buyer | reads the seller's board, picks a task within its limit | with the buyer |
| 2 | buyer | reads the `402`, checks it, funds the order, asks again | in the order |
| 3 | seller | delivers against the funded order | in the order |
| 4 | evaluator | accepts: the signed acceptance reaches the program | with the seller, the amount whole |
| 4, wrong work | evaluator | does not accept: no signature exists | in the order |
| 5, wrong work | anyone | sends the refund after the deadline | with the buyer, the amount and the fee |

`python -m pytest -q tests/test_agent_pays_agent.py` runs both endings against the test builds of `knos_pay` and
`knos-oidc` in LiteSVM, the two agents as separate processes. In the wrong-work run it also shows that a signature
from a workflow other than the one the order pinned is refused, and that a refund before the deadline is refused.
The evaluator's signature is GitHub's, over a run of the order's pinned workflow; in the test a test key that only
a test build trusts signs in its place. The devnet commands are in the example's README; that run has not been made.

## Record: a lookup priced for machines

The Record line of the price book is 0.10 USD a lookup, paid per call by whoever reads a supplier's record: an
agent, a marketplace, an underwriter. [`examples/record_api`](../examples/record_api) is that line under this
scheme, as a server anyone can run (`python -m knos.record_api`, [`src/knos/record_api.py`](../src/knos/record_api.py)).
**Knos hosts none**, the record file and its page stay free ([RECORD.md](RECORD.md)), and no outside caller has
paid for a lookup.

| | the scheme above | a record lookup |
|---|---|---|
| what one order buys | one delivery | a pack of fifty lookups at 0.10 test USDC |
| the payment proof | the order's address | the order's address, `n`, and the funding wallet's signature over `knos-record:<order>:<n>:<slug>` |
| a replay | "this order already paid for one delivery" | "this payment was already used": `n` was served |
| the requirement | `accepts[0]` | the same, with `extra.record` = `{price, lookups, sign, free}` |

Two things in the program shape it. The smallest order `knos_pay` takes is 5.00, so a lookup cannot be an order of
its own: one order is a pack, and the fee of an order (at least 0.05) is paid once per pack. And an order's address
is public, so naming it proves nothing: each call is signed by the wallet that funded the order, and the server
counts.

`python -m pytest -q tests/test_record_api.py` runs it against the test builds in LiteSVM with two stand-in agents:
the first pays and reads; its payment replayed is refused; the second cannot spend the first's order and funds its
own; the fifty-first lookup is refused; a signed acceptance pays the seller the pack; an order nobody accepted goes
back to its caller after the deadline. Not built: a judge that signs for lookups served (a test key signs in the
test), a refund of unused lookups and a price below a pack. On devnet it has run once, with the release run's own
wallets as caller and seller: one paid lookup ([examples/record_api](../examples/record_api/README.md)).

## Other rails: where the same acceptance would plug in

**No adapter for either of these is built, and nothing has been proposed to either project.** Each paragraph says
what an adapter would have to be, from the specification as it was read on 6 October 2026.

**Tempo's Machine Payments Protocol.** Its core is an HTTP authentication scheme
([The "Payment" HTTP Authentication Scheme](https://paymentauth.org/draft-httpauth-payment-01.html), draft 01,
dated 5 October 2026; the specifications are at [paymentauth.org](https://paymentauth.org)): the server answers
`402` with `WWW-Authenticate: Payment` carrying `id`, `realm`, `method`, `intent` and a base64url `request`; the
client retries with `Authorization: Payment`; the server answers with a `Payment-Receipt`. An intent says what kind
of payment is asked for (`charge`, `session` and `subscription` are specified) and a method says on which network;
both are registered by publishing a specification. The `session` intent on Tempo
([draft-tempo-session-00](https://paymentauth.org/draft-tempo-session-00.html)) sets funds aside in an escrow the
client opens, and the server draws on it with vouchers the client signs; nothing in it waits for a third party to
accept the work. The Knos acceptance would plug in as a **new intent**, not as a change to `session`: its `request`
would carry what `knos-order`'s `extra` carries (the program, the terms and their hash, the pinned workflows, the
deadline), the credential would be the funded order's address, and the server would verify it by reading the order.
The open point is the receipt: that draft issues a `Payment-Receipt` on successful payment, and in this scheme the
seller has not been paid when the resource is served, only when the acceptance is signed.

**ERC-8183, Agentic Commerce** ([EIP-8183](https://eips.ethereum.org/EIPS/eip-8183), a draft created on 25
February 2026; [discussion](https://ethereum-magicians.org/t/erc-8183-agentic-commerce/27902)). A job has a client,
a provider and one evaluator address fixed at creation. The client funds an escrow, the provider calls `submit`
with a `bytes32` reference to the deliverable, and then only the evaluator may call `complete` (the escrow pays the
provider) or `reject` (it refunds the client); after `expiredAt` anyone may call `claimRefund`, which no hook can
block. The specification says the evaluator may be a smart contract that performs its own checks, and `complete`
takes a `bytes32 reason` meant for a commitment to the evidence. That evaluator slot is where the Knos acceptance
fits: a contract set as the job's evaluator that calls `complete` only when it is handed an issuer-signed token it
has verified itself, whose audience names the job and the deliverable, and that passes the terms hash as `reason`.
It needs the RS256 verifier written for the EVM. `knos-oidc` exists on Solana only, and carrying its result across
chains would put an oracle back in the middle, so that is not offered as the adapter.

## Run it

Three ways, from the least to the most real. The server (`server.mjs`) and the client (`client.mjs`) are the same
files in all three; only the chain behind them changes.

**1. Replayed, with no chain and no key.**

```
node --test examples/x402_attested/test.mjs
```

An HTTP server and a client in one test. The chain is replayed from `fixtures.json`: the funding instruction, the
Order account and the log lines are what the test build of `knos_pay` did in LiteSVM (`scripts/x402_fixture.py`
writes them). The client's `FundOrderWallet` must be, byte for byte, the instruction LiteSVM accepted.

**2. Live against the program, over JSON-RPC, on this machine.**

```
python -m pytest -q tests/test_x402_attested.py -k live
```

`live.mjs` takes `--rpc <url>` and talks to nothing else: it reads accounts with `getAccountInfo`, signs the
funding transaction itself (Node's Ed25519, a key file as `solana-keygen` writes it), sends it with
`sendTransaction`, and reads an order's history with `getSignaturesForAddress` and `getTransaction`. In the test the
URL is `tests/_rpc_shim.py`: those methods in front of LiteSVM with the test builds of `knos_pay` and `knos-oidc`
loaded, signatures verified. So the program runs: the test reads the order the client funded, pays it with a token
from the order's pinned workflow (signed by the test key a test build trusts, in place of GitHub's), and sees
`status` report `paid`; in a second run it moves the clock past the deadline and `live.mjs refund` returns the
amount and the fee. `live.mjs refund` before the deadline is refused by the program.

**3. On devnet, with test USDC.** The command the release step runs, now that `knos_pay` 2.1 is the build at
`5y7iWJ1VAMJjnnWbbdo2a2PsWJEwTExSNpzrvQSEnS8k` (work orders are new in 2.1; until its upgrade, proposal 4, executed,
devnet refused `FundOrderWallet` and this step could not run):

```
cp examples/x402_attested/offer.devnet.json offer.json      # fill repoId, issue, wfSha, seller, delivery
node examples/x402_attested/live.mjs run    --rpc https://api.devnet.solana.com --key buyer.json --offer offer.json
node examples/x402_attested/live.mjs status --rpc https://api.devnet.solana.com --order <the order it printed>
node examples/x402_attested/live.mjs refund --rpc https://api.devnet.solana.com --key buyer.json --order <the order>
```

`buyer.json` is a devnet key with a little SOL and at least 5.40 test USDC (5.05 once knos_pay 2.2 is live; Circle's devnet mint
`4zMMC9srt5Ri5X14GAgXhaHii3GnPAEERYPJgZJDncDU`, from [faucet.circle.com](https://faucet.circle.com)): 5 for the
order and its fee: 0.40 under the 0.3.14 fee the public program charges today, 0.05 from knos_pay 2.2. The offer's `repoId` and `issue` name a real issue, `wfSha` the commit of
`drexthealpha/knos-workflows` that the repository's `prove.yml` is pinned to, and `seller` the account that will
deliver. `run` prints the order's address and the funding transaction's signature. The order is then settled one of
two ways, and `status` says which: the seller's pull request is merged and the pinned workflow's GitHub-signed token
pays it (`paid`), or nobody delivers and, after the offer's 15 minutes, `refund` returns everything to the buyer
(`refunded`). `serve` and `buy` run the two sides as separate processes on separate machines.

**This run was made on devnet on the release's staging deployment of knos_pay 2.1**, not on the pinned program,
which refused `FundOrderWallet` until its upgrade executed: `run` funded an order of 5.00, the resource was served,
and the seller was paid when the pull request was accepted. The two transactions are in
[CAPABILITIES.md](CAPABILITIES.md), "The 0.3.14 rehearsal on devnet", and the payment's signature is in the note of
the x402 entry of `docs/capabilities.json`, which stays `tested` until the scheme runs at the public program ids.

The example needs Node 20 and nothing else: its only import outside Node is [`sdk/settle`](../sdk/settle), which has
no dependency.
