# x402 "knos-order": pay on signed acceptance, not before delivery

**This is a proposal. It is not part of x402**, it is not registered with the x402 Foundation, and no facilitator
other than the resource server itself implements it. It is written so that someone could.

How much x402 carries, by its own count: [x402.org](https://www.x402.org) showed, for the last 30 days, 75.41M
transactions, $24.24M of volume, 94.06K buyers and 22K sellers when it was read on 6 October 2026. That is the
figure used here, because anyone can open the page and check it; larger cumulative figures quoted elsewhere are
not. None of that volume is Knos's: `knos-order` has moved test USDC on devnet only.

## What is missing in x402 today

x402 lets a server answer `402 Payment Required` with a machine-readable price, and a client pay and ask again. A
*scheme* says how the payment is authorised and settled. The schemes the specification repository defines move money
at or before delivery, or leave the decision with the seller: `exact` transfers a fixed amount, `upto` a metered
one, `batch-settlement` settles a channel, and `auth-capture` holds the money until the resource server captures,
voids or refunds it
([x402 specification v2](https://github.com/x402-foundation/x402/blob/main/specs/x402-specification-v2.md), and the
schemes under `specs/schemes`, read on 6 October 2026). None conditions the payment on the thing delivered being
accepted by someone who is neither the buyer nor the seller. For an API call
that is right: the response is the delivery. For work (a fix, a build, a review) it is not: the buyer pays for a
result, and the result is judged after the response.

## The scheme

`knos-order` makes the payment requirement a **Knos work order**: an escrow on Solana that pays when GitHub signs
that the order's terms were met, and returns the money to its funder if nobody delivers.

1. The client asks for the resource. It may name its wallet in an `Attested-Payer` header.
2. The server answers `402` with one `accepts` entry of scheme `knos-order`. It names the order to fund: the program,
   the order's address (when the client named its wallet; otherwise `null` and the client derives it), the terms
   and their hash, the amount, the mint, the fee the funder pays on top, and the workflows whose signed run is the
   judge.
3. The client checks the requirement against its own limits, derives the order's address itself, and funds the
   order with `knos_pay`'s `FundOrderWallet`. Its money is now in the order's own token account. Nobody holds a key
   to it.
4. The client asks again with `PAYMENT-SIGNATURE`: the order's address is the payment proof.
5. The server reads the order from the chain (it is `knos_pay`'s, for this issue, these terms, this amount, these
   workflows, open, with time left) and delivers. Its `PAYMENT-RESPONSE` says `escrowed`: the seller has not been
   paid yet.
6. **The seller is paid when the acceptance lands**: the order's pinned workflow runs, GitHub signs a token that
   names the order and the payee, `knos-oidc` verifies the signature on chain and `PayOrder` pays the payee the
   amount whole. If that never happens, anyone sends `RefundOrder` after the deadline and the amount and the fee
   return to the client.

Headers and objects are x402 v2's: `PAYMENT-REQUIRED`, `PAYMENT-SIGNATURE` and `PAYMENT-RESPONSE`, each the base64 of
the JSON below ([HTTP transport v2](https://github.com/x402-foundation/x402/blob/main/specs/transports-v2/http.md)). The
only new header is `Attested-Payer` on the first request, and it is optional.

The name follows the specification's own: a scheme is a lower-case word in `accepts[].scheme` (`exact`, `upto`,
`auth-capture`, `batch-settlement`), specified per network family in `specs/schemes/<scheme>/scheme_<scheme>_<family>.md`; this page
is what `specs/schemes/knos-order/scheme_knos_order_svm.md` would hold. What is not a payment field travels as an
extension, which the specification defines as `{ info, schema }` under a key of `extensions`: the key here is
`knos-order`, `schema` is the JSON Schema of `info`, and a client that does not know the extension ignores it. A
server can offer `exact` beside it in the same `accepts` list: a client that knows only `exact` pays before delivery
as it does today.

| x402 field | in `knos-order` |
|---|---|
| `scheme` | `"knos-order"` |
| `network` | the cluster, as x402 names it (`solana:EtWTRABZaYq6iMfeYKouRu166VU2xqa1` is devnet) |
| `amount` | what the payees receive, in the mint's smallest units. The funder pays `extra.fee` on top |
| `asset` | the mint |
| `payTo` | the seller's wallet. The escrow pays it, not the client; the judge's token names the payee |
| `maxTimeoutSeconds` | the order's work time: after it, an unpaid order can be refunded |
| `extra.program` | `knos_pay`'s address on that cluster |
| `extra.order` | the order's address for the named payer, or `null` |
| `extra.repoId`, `extra.issue`, `extra.seq` | what the order is for: its scope is `sha256("knos3:scope" || repoId || issue)` and its address `["ord", scope, payer, seq]` |
| `extra.terms`, `extra.termsHash`, `extra.mode` | the acceptance terms (a JSON document), their sha256, and how they are judged |
| `extra.workflows` | the repository and commit of the workflows whose GitHub-signed run pays the order |
| `extra.fee` | `knos_pay`'s fee for this amount, paid by the funder on top: 2.5% of the first 1,000, 1% to 50,000, 0.5% above; at least 0.40 |
| `extra.payee.githubId` | who the seller is to the judge |

## What each side must check

The client, before it signs: the program is one it knows; the mint and the amount are within its limits;
`termsHash` is the hash of `terms`; `fee` is the program's fee for the amount; `extra.order`, when given, is the
address its own wallet's funding creates. The server, before it delivers: the account at `payload.order` is owned
by the program, is an Order whose own fields derive that address, is for this scope, mint, terms, mode and
workflows, holds at least the amount, is open, has enough time left, and has not paid for a delivery before.
Neither trusts the other's arithmetic, and neither can move the escrow.

## What it does not do

- It does not make delivery atomic. The server delivers against escrow and carries the risk that the acceptance
  never comes; the client carries the risk that the delivery is not what the terms describe, and is then refunded
  after the deadline, not before.
- The judge is GitHub-shaped: a workflow run whose token GitHub signs. An acceptance that no workflow can decide
  cannot be expressed.
- The public x402 facilitator is not involved, and whether its allow-list would take a program it does not know
  was not confirmed. The resource server verifies for itself.
- No facilitator but Knos's own example implements the scheme, and no pull request for it has been opened on the
  specification repository. What a facilitator would have to do is small and is written down below.
- Amounts are bounded by `knos_pay`: at least 5 and at most 100,000 whole units of the mint per order (the devnet
  build's cap).

## What a facilitator does in this scheme

Less than in any other: it signs nothing, pays no fee and can move no money. `/verify` reads the account at
`payload.order` and applies the server's checks above; `/settle` reads it again and answers `escrowed`. The escrow
program pays or refunds later, with no facilitator in the path.

The way a scheme is proposed there, as the repository's `specs/CONTRIBUTING.md` had it on 6 October 2026: open an
issue with the problem and the approach; write `specs/schemes/<name>/scheme_<name>.md` from `scheme_template.md`
and one `scheme_<name>_<network>.md` per network from `scheme_impl_template.md`; open a pull request. Code for a
Solana facilitator lives in `typescript/packages/mechanisms/svm`, one class per scheme that implements
`SchemeNetworkFacilitator`. A change in that shape has been prepared for `knos-order` (the two specification files,
a `verify` and `settle` handler for devnet, and unit tests against an order the escrow wrote) and **has not been
submitted**: this page will link the pull request when there is one, and until then the count of outside
facilitators is 0.

## Run it

Three ways, from the least to the most real. The server (`server.mjs`) and the client (`client.mjs`) are the same
files in all three; only the chain behind them changes.

**1. Replayed, with no chain and no key.**

```
node --test examples/x402_attested/test.mjs
```

An HTTP server and a client in one test. The chain is replayed from `fixtures.json`: the funding instruction, the
Order account and the log lines are what the test build of `knos_pay` did in LiteSVM (`scripts/x402_fixture.py`
writes them). The client's `FundOrderWallet` must be, byte for byte, the instruction LiteSVM accepted.

**2. Live against the program, over JSON-RPC, on this machine.**

```
python -m pytest -q tests/test_x402_attested.py -k live
```

`live.mjs` takes `--rpc <url>` and talks to nothing else: it reads accounts with `getAccountInfo`, signs the
funding transaction itself (Node's Ed25519, a key file as `solana-keygen` writes it), sends it with
`sendTransaction`, and reads an order's history with `getSignaturesForAddress` and `getTransaction`. In the test the
URL is `tests/_rpc_shim.py`: those methods in front of LiteSVM with the test builds of `knos_pay` and `knos-oidc`
loaded, signatures verified. So the program runs: the test reads the order the client funded, pays it with a token
from the order's pinned workflow (signed by the test key a test build trusts, in place of GitHub's), and sees
`status` report `paid`; in a second run it moves the clock past the deadline and `live.mjs refund` returns the
amount and the fee. `live.mjs refund` before the deadline is refused by the program.

**3. On devnet, with test USDC.** The command the release step runs, once `knos_pay` 2.1 is the build at
`5y7iWJ1VAMJjnnWbbdo2a2PsWJEwTExSNpzrvQSEnS8k` (work orders are new in 2.1; until its upgrade has executed, devnet
refuses `FundOrderWallet` and this step cannot run):

```
cp examples/x402_attested/offer.devnet.json offer.json      # fill repoId, issue, wfSha, seller, delivery
node examples/x402_attested/live.mjs run    --rpc https://api.devnet.solana.com --key buyer.json --offer offer.json
node examples/x402_attested/live.mjs status --rpc https://api.devnet.solana.com --order <the order it printed>
node examples/x402_attested/live.mjs refund --rpc https://api.devnet.solana.com --key buyer.json --order <the order>
```

`buyer.json` is a devnet key with a little SOL and at least 5.40 test USDC (Circle's devnet mint
`4zMMC9srt5Ri5X14GAgXhaHii3GnPAEERYPJgZJDncDU`, from [faucet.circle.com](https://faucet.circle.com)): 5 for the
order and the 0.40 fee. The offer's `repoId` and `issue` name a real issue, `wfSha` the commit of
`drexthealpha/knos-workflows` that the repository's `prove.yml` is pinned to, and `seller` the account that will
deliver. `run` prints the order's address and the funding transaction's signature. The order is then settled one of
two ways, and `status` says which: the seller's pull request is merged and the pinned workflow's GitHub-signed token
pays it (`paid`), or nobody delivers and, after the offer's 15 minutes, `refund` returns everything to the buyer
(`refunded`). `serve` and `buy` run the two sides as separate processes on separate machines.

**This run was made on devnet on the release's staging deployment of knos_pay 2.1**, not on the pinned program,
which refuses `FundOrderWallet` until its upgrade executes: `run` funded an order of 5.00, the resource was served,
and the seller was paid when the pull request was accepted. The two transactions are in
[CAPABILITIES.md](CAPABILITIES.md), "The 0.3.14 rehearsal on devnet", and the payment's signature is in the note of
the x402 entry of `docs/capabilities.json`, which stays `tested` until the scheme runs at the public program ids.

The example needs Node 20 and nothing else: its only import outside Node is [`sdk/settle`](../sdk/settle), which has
no dependency.
