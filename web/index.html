Knos is the neutral count and settlement for software work priced per outcome: terms fixed before the work, a signed CI run attests they were met, a Solana program counts it or pays it.

What is here

  • A verifier on Solana for any RS256 workload identity, readable by other programs.
  • Named checks and allowed paths, hashed into the order at funding.
  • A seller who can settle without the buyer.
  • Payment on a black-box check: 0 of 63 cheating pull requests passed it, 56 passed plain CI.
  • A neutral count of accepted outcomes, with no escrow.

A work order is a task, its budget and the terms that decide whether it is done, fixed before the work starts. A bounty on an issue is the smallest work order. When the work is merged, a workflow run that GitHub signs says whether the terms were met, and a Solana program checks that signature itself before it pays. No person holds the money in between.

Protect a repository

One file, .github/workflows/knos.yml, is the whole payment flow. A second file, .github/workflows/knos-check.yml, is optional: the check on every pull request. Neither needs a wallet or a secret.

Only the payment flow, by one pull request and with terms from a template: Install.

What knos.yml does

  • Answers every comment with a line that starts with /knos, on issues and on pull requests. /knos help lists the commands.
  • On /knos fund (or a new issue whose description has that line), asks GitHub to sign a statement for one action: fund this task from this Balance. Anyone may carry a statement to Solana; it does only what it names, once.
  • On a push to the default branch, for each merged pull request that closes a funded issue: reads GitHub's record of the merged commit against the task's funded terms, and only when every funded check passed and the changed files are in scope asks GitHub to sign the statement that pays.
  • Comments on issues and pull requests, and assigns an issue for /knos take.
  • Can be started by hand (Actions, then knos, then Run workflow, with a merged pull request's number) to try a payment again.

What it cannot do

  • Hold or move money. It has no wallet and no bounty's money. Money moves only on Solana, after the program has checked GitHub's signature, and only as the statement and the task's terms say.
  • Change your code, branches or settings: it can read, comment and assign, and nothing else.
  • Spend a Balance past what its wallet allowed: only comments by the Balance's owner and the people it lists count, and no task takes more than its cap.
  • Change a task's terms after funding, or take a payment back once it has been attested.
  • Be changed by a pull request: it runs from the default branch, it does not use pull_request_target, and a pull request that edits .github/ or .knos/ is out of a task's scope.
  • Vouch for more than its repository can: GitHub signs which workflow ran, at which commit, in which repository, not what it read there. So a task's checks are judged in the funder's own repository, about the funder's own money.

No secret is needed. The signed statements are posted as comments and Knos's public relay carries them to Solana and pays the fees. Optional: a repository secret KNOS_RELAY_KEY, a Solana key with a little SOL for fees and never a bounty's money, lets the jobs carry their own statements instead of waiting for the relay.

The optional second file, knos-check.yml, checks every pull request, forks included, and moves no money. It reads, and it reports through its own status (check / claims) and the job's summary. A first-time contributor's first run waits for a maintainer's approval on the pull request's page. GitHub runs it as the pull request has it, so a pull request can change it for its own run: that is why it is advice, and nothing about money depends on it. With the first file alone everything about money works; /knos status on a pull request then tells its author what the check would have said.

Fund a task

One comment on an issue, by the repository's owner or by someone the owner's Balance lists.

The comment

/knos fund 20 checks: test
/knos fund
The command: a line of the comment (or of a new issue's description) that starts with it. /knos bounty means the same.
20
The amount, from 5 to 100,000 test USDC, with at most 6 decimals. A build for real money sets its own cap.
checks: test
The checks that must have concluded success at the merged pull request's last commit, by name, separated by commas. Left out, the task takes the default branch's required status checks, or, when it requires none, the checks that ran on its latest commit. checks: none asks for none: your merge alone is then the acceptance.
Optional
paths: src/** (the pull request may change only files that match), days 30 (when an unpaid task's money goes back: 14 days unless you say, 90 at most) and reserve 3 (how many days /knos take holds the task for one person: 7 unless you say).

What the reply says

Knos: 20.00 test USDC is in escrow for issue #7. It is paid when a maintainer merges a pull request that closes this issue, if these checks passed at that pull request's last commit: test (the checks you named). The pull request may not change .github/** or .knos/**. If it is not paid by its deadline, the money goes back to where it came from. To earn it: open a pull request whose description says Fixes #7. /knos take reserves the issue for 7 days. For the money to reach you when it is paid, comment /knos address <your Solana address> on your pull request; without an address it waits for you until you bind a wallet (180 days at most).

That is the shape of the reply. The terms in it are fixed: the funding transaction logs them and the task stores their hash, so they cannot change afterwards. Knos answers on the issue when the money is in escrow, or says what went wrong and what to type instead. How long that takes is measured, not promised: see Numbers.

Every /knos comment gets a reply, and /knos help lists the commands: among them /knos take (reserve a funded task), /knos status, /knos reject (a maintainer, before merging: this pull request does not take the bounty) and /knos tip.

Payment without a merge. Payment without a merge ("tests mode") is offered only when the acceptance bundle is black-box: the submission runs as a separate process and only its output is compared. Everything else is funded in merge mode, as above. The reason is measured: of 63 cheating pull requests in the tamper benchmark, plain CI passed 56, acceptance tests that run in the same process as the code passed 7, and the black-box check passed none.

Add money

A comment spends a Balance: test USDC that a wallet set aside for the repositories of one GitHub owner (a person or an organisation). The wallet that opened it says which people may spend it by comment (up to four besides the owner) and how much one task may take, and only that wallet can take unspent money back. A Balance that lists the commenter and holds the amount is spent first. When none can pay, on devnet, the escrow's faucet gives the amount as free test USDC: at most 100 per comment, once per repository per minute. Faucet money cannot be withdrawn, and every record counts it apart.

What is in escrow for an issue?

How it pays. A task is paid when a maintainer merges a pull request that closes the issue and its funded checks passed at that pull request's last commit. There is no waiting period after the merge: the payment is final. A maintainer who does not want a pull request to take the bounty comments /knos reject on it before merging. With no payment by the deadline the money goes back where it came from, and that needs no token. Fee: paid by the funder on top of the amount, 2.5% of the first 1,000, 1% from 1,000 to 50,000 and 0.5% above (at least 0.40 test USDC, no maximum), and only when someone is paid: a refund returns it with the amount. Pricing says which fee the program on devnet applies today.

Get paid

A task pays the person whose pull request is merged for it. You need no wallet to do the work. Three ways to be paid, simplest first.

Solana devnet. What is paid here is test USDC.

  1. Say where, on your pull request

    Comment on it:

    /knos address YOUR_SOLANA_ADDRESS

    The payment goes to that address when the pull request is merged and the payment is attested. Do not edit the comment: an edited comment does not count. To change the address, post a new one.

  2. Or bind a wallet once

    Every task then pays that wallet, whatever a pull request says: a bound wallet comes first. You do it by hand on GitHub, in two steps:

    1. Create a repository from the template drexthealpha/knos-claim (“Use this template”). Keep the name knos-claim and make it public, in your own account (a personal account, not an organisation).
    2. Open that repository's Actions tab, choose knos claim, press Run workflow and paste your Solana address into the box yourself.

    Or from a terminal, one command does both steps:

    knos claim YOUR_SOLANA_ADDRESS

    Why by hand: an address carried in a link could be someone else's, so the address has to be one you typed. The run asks GitHub to sign that the owner of the repository names that address; the escrow takes that signature only from a run started by hand, by the owner, in a repository named knos-claim in their account. A later binding replaces an earlier one.

  3. Or do nothing yet

    With no address on the pull request and no bound wallet, the money is held for you for 180 days. Bind a wallet in that time and what is held can be sent to it (/knos settle on the merged pull request tries again). After 180 days it goes back to the funder.

A pull request that an agent opened under a bot account pays a person only when GitHub shows whose it is: the issue is assigned to exactly one person (a maintainer assigned them, or they commented /knos take), or a maintainer commented /knos pay @login on the pull request, or a person named in its assignees commented /knos mine on it. A line in the description never decides.

Build on it

    
knos-oidc is a Solana program that verifies a GitHub Actions or GitLab CI token
      on chain. Any program can then require a fact that GitHub signed: which repository, which commit, which
      workflow, which account ran it.

    

      
Use it from your program

      
A verified token is an account owned by knos-oidc. Read it; do not call anything. The interface crate has no
        dependency, so it builds with solana-program, pinocchio or anchor of any version.

How the signing keys are admitted

      
    
        
  • GitHub's keys are in the program from the start. Any other key enters only on a token GitHub signed for the
          rotate workflow at its fixed commit, waits a day and needs the guardian's approval. Every key, the first ones
          too, stops working after 30 days unless a token from that workflow attests it again. Nobody registers a key
          by hand.
    • 
        
  • The guardian can approve a key and revoke one for good. It cannot add a key, and it cannot change a delay
          or an expiry. Which keys are on chain, and until when, is on Numbers.
    • 
        
  • Who can change the program is read from Solana on Numbers.
