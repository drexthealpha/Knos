How it works

This runs on Solana devnet, a test network: the money is test USDC and worth nothing.

Why Solana?

Money is released with no custodian, and neither buyer nor supplier can change the count. One person holds every upgrade key today; a program change waits 8 days in public.

You can check a receipt without Solana. Solana moves the money and stores one fingerprint of all the receipts.

  1. Agree the terms

    Name the checks before the work starts. Fund a task

    /knos fund 20 checks: test
    Versioned terms: the whole contract

    A versioned document of ten fields: what one deliverable is, who referees, who hears an appeal, who may change the terms. An order cites one version. The terms document.

    Holdbacks: a share kept for a warranty

    A share of the payment stays in the order for the warranty. If the change is undone during the warranty, GitHub signs that, and the share goes back to the funder. Disputes and warranties.

  2. A third party signs the result

    GitHub signs which workflow ran, and where. Protect a repository

    GitHub signs: repository sha job_workflow_ref
    Five parts of a receipt

    Every receipt reads as identity, execution, acceptance, consequence and assurance: who signed, what ran, which test passed, what became payable, and what you still have to trust. The five parts.

  3. Both sides get the same bill, and the money moves

    Buyer and supplier each rebuild the same bill from what GitHub signed. Get paid

    Paid on devnet, as a demonstration: 4PovnMjD…2zcDxt
    Netting: small tickets, one release

    Small payments are added up outside Solana and paid as one transfer per supplier per period. Netting.

    Reserves: money locked before the work

    A buyer locks money for one supplier before the work; the added-up payments are taken from it. Reserves.

    Exits: leave before an upgrade

    Any change to Knos's programs is shown in public eight days before it can run. knos exit --before-upgrade lists what you hold and its way out. Governance.

One transaction, end to end
  • Fund the order in test USDC under terms fixed first.
  • Reject the first work: a check failed, nothing paid.
  • Accept the corrected work: GitHub signs the passing run.
  • Pay the supplier once the program checks GitHub's signature.
  • Refuse a replay of the same proof: nothing paid twice.
  • Rebuild the invoice on both sides: one line, agreed.

  • A supplier can collect payment without waiting for the buyer.

    Protect a repository

    Add one workflow file. It needs no secret.

    The two files

    .github/workflows/knos.yml is the whole payment flow. .github/workflows/knos-check.yml is optional: the check on every pull request.

    Install with one pull request

    What the file does: five jobs
    • Answers every /knos comment. /knos help lists the commands.
    • On /knos fund: asks GitHub to sign one statement that funds this task. Anyone may send it to Solana; it can be used once.
    • On a merge that closes a funded issue: reads GitHub's record against the funded terms, and asks GitHub to sign the payment only when every funded check passed and the changed files are in scope.
    • Comments, and assigns an issue for /knos take.
    • Runs by hand (Actions, knos, Run workflow) to try a payment again.
    What it cannot do: six limits
    • Hold or move money. It has no wallet. Money moves only on Solana, after the program has checked GitHub's signature.
    • Change your code, branches or settings: it can read, comment and assign.
    • Spend a Balance past its limits: only its owner's and listed people's comments count, and no task takes more than its cap.
    • Change a task's terms after funding, or take back a payment GitHub has signed for.
    • Be changed by a pull request: it runs from the default branch and never uses pull_request_target.
    • Vouch for more than its repository can: GitHub signs which workflow ran, at which commit, in which repository, not what it read there.

    No secret is needed: Knos's public relay (a server that sends signed statements to Solana) sends them and pays the network fees. Each limit in full, and the optional relay key.

    The optional check file

    knos-check.yml checks every pull request, forks included, and moves no money. It reports through its own status, check / claims. A pull request can change it for its own run, so it is advice: nothing about money depends on it. The second file in full.

    Fund a task

    Comment on an issue. The checks you name are the terms.

    The comment

    /knos fund 20 checks: test
    Each part of the comment
    /knos fund
    A line of a comment, or of a new issue's description, that starts with it. /knos bounty means the same.
    20
    The amount, from 5 to 100,000 test USDC, with at most 6 decimals. A version that uses real money would set its own maximum.
    checks: test
    The checks that must pass on the merged pull request's last commit. If you name none, Knos uses the default branch's required checks, or else the checks that ran on its latest commit. checks: none: your merge alone is the acceptance.
    Optional
    paths: src/** (the only files a pull request may change), days 30 (when unpaid money goes back: 14 days unless you say, 90 at most), reserve 3 (days /knos take holds the task: 7 unless you say).
    What the reply says
    Knos: 20.00 test USDC is held for issue #7 until the proof passes. It is paid when a maintainer merges a pull request that closes this issue, if these checks passed at that pull request's last commit: test (the checks you named). The pull request may not change .github/** or .knos/**. If it is not paid by its deadline, the money goes back to where it came from. To earn it: open a pull request whose description says Fixes #7. /knos take reserves the issue for 7 days. For the money to reach you when it is paid, comment /knos address <your Solana address> on your pull request; without an address it waits for you until you bind a wallet (180 days at most).
    Who may fund, fixed terms, tests mode

    Who may fund: the repository's owner, or someone the owner's Balance lists.

    The terms are fixed: the funding transaction logs them and the task stores their hash. How long a reply takes is measured: see Numbers.

    Every /knos comment gets a reply. /knos help lists the commands: /knos take, /knos status, /knos reject, /knos tip.

    Payment without a merge is offered only for a black-box check: the submission runs as a separate process and only its output is compared. Of 63 cheating pull requests in the tamper benchmark, plain CI passed 56, in-process acceptance tests passed 7 and the black-box check passed none.

    Add money

    What a Balance is

    A comment spends a Balance. A Balance is test USDC that one wallet sets aside for one GitHub owner's repositories. That wallet picks who may spend it (up to four people besides the owner) and the most one task may take. Only that wallet can take unspent money back. With no Balance, the devnet faucet gives free test USDC: at most 100 per comment, once per repository per minute. Faucet money cannot be withdrawn and is counted apart. A Balance in full.

    1. Set the wallet to devnet first. Get test USDC
    2. Another token

      Prefilled with Circle's devnet test USDC. Standard Solana tokens work. The program refuses a token that can block or tax a transfer.

    What is held for an issue?

    How it pays, the fee

    A task is paid when a maintainer merges a pull request that closes the issue and its funded checks passed at the last commit. The payment is final. /knos reject before merging keeps a pull request from the bounty. Unpaid by the deadline, the money goes back; that needs no token.

    Fee: 0.30% of the amount, at least 0.05 test USDC, paid by the funder on top (knos_pay 2.2 is live). Orders funded before the upgrade keep the rate fixed at their funding.

    There is no maximum. It is charged only when someone is paid: a refund returns it with the amount. An order funded under knos_pay 2.1 keeps its stored fee: 2.5% of the first 1,000, 1% to 50,000, 0.5% above, at least 0.40 test USDC. Pricing says which fee the program on devnet applies today.

    A task with no repository

    How a task is checked

    State the task as five or more pairs: an input and the answer it must get. Knos pays the first solution whose command prints every answer; its code runs as a separate process and only what it prints is compared. It sends nothing: you press the last button on each GitHub page yourself.

    How the command runs

    It runs in the pull request's tree, with one input line on standard input. What it prints is compared with the answer; spaces at the end of a line and blank lines at the ends are ignored.

    Pairs: an input line, and the answer it must get

    Get paid for merged work

    Merge the work. Say where to be paid.

    Devnet: test USDC.

    1. Comment your address

      /knos address YOUR_SOLANA_ADDRESS
      When the address counts

      Comment on your own pull request. It is paid to that address once the pull request is merged and GitHub has signed the run that pays it. An edited comment does not count: to change the address, post a new one.

      Who is paid: the person whose pull request is merged for the task. You need no wallet to do the work.

    2. Or bind a wallet once

      A bound wallet comes first, whatever a pull request says. Three steps, by hand:

      1. Create an empty repository named knos-claim. Keep the name knos-claim and make it public, in your own account (a personal account, not an organisation).
      2. Add its one file: knos-claim.yml from Knos, as .github/workflows/knos-claim.yml (Add file, Create new file, paste, Commit changes). The payout page, #payee=YOUR_LOGIN, fills it in for you.
      3. Open that repository's Actions tab and choose knos claim. Press Run workflow and paste your Solana address yourself.

      Or from a terminal, one command does all three:

      knos claim YOUR_SOLANA_ADDRESS

      Why by hand: an address carried in a link could be someone else's, so you type it. GitHub signs that the repository's owner names that address; the payment program takes that signature only from a run started by hand, by the owner, in a repository named knos-claim. A later binding replaces an earlier one.

    3. Or do nothing yet

      With no address and no bound wallet, the money is held for you for 180 days. Bind a wallet in that time and /knos settle on the merged pull request sends it. After 180 days it goes back to the funder.

    When an agent opened it

    A bot account's pull request pays a person only when GitHub shows whose it is: the issue is assigned to one person, a maintainer commented /knos pay @login, or an assignee commented /knos mine. A line in the description never decides.

Key rules

      
  
    • GitHub's keys are built in. Any other key enters only on a token GitHub signed for the rotate workflow at its
    fixed commit, waits a day and needs the guardian's approval.
      • 
  
    • Every key stops working after 30 days unless that workflow attests it again. Nobody registers a key by hand.
      • 
  
    • The guardian can approve a key or revoke one for good. It cannot add a key or change a delay.
      • 
  
    • The programs are upgradeable only through a multisig with a public 8-day delay, until an outside review.
