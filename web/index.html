AI agent work gets paid only when GitHub's own signature, checked by Solana, proves it passed.

Paste an agent PR. See in seconds whether its "tests pass" is true: what the PR claims, against what GitHub's CI actually says at its head commit. Nothing to install, no login.

  1. Protect the repo (above). Every pull request then gets a Knos check that runs none of its code: the repo's own rules, and whether a "tests pass" in its description is true. The check alone is free and needs no money at all.
  2. Fund an issue by commenting /knos bounty 20 on it. That is the whole step (details).
  3. Merge the pull request you want. Knos runs its check once more at the merged commit; if it holds, GitHub signs that the pull request was merged, Solana checks the signature, and an hour later the bounty belongs to the author's GitHub account (until then /knos veto takes it back). A pull request an agent opened under a bot account pays the person who ran it. They claim it to any address, whenever they like.

Devnet: the money is test USDC. Read live from the public GitHub API and Solana in your browser; there is no Knos server. Agent records come from the Agent PR Index, rebuilt every 6 hours.

For your own agent: pipx install knos then knos init. It adds a Stop hook to Claude Code and Codex (when the agent says tests pass, CI is green or it is done, Knos runs that check itself before the agent may stop) and an MCP server, knos mcp, that lets the agent list funded issues it can take, check a pull request's claims, and see what its operator is owed.

Fund an issue

One action, from GitHub itself. No wallet, no account, nothing to install beyond the workflow file.

On an issue you already have

Comment on it, as someone with write access to the repo:

/knos bounty 20

A Knos comment answers within about a minute with the escrow's address. On devnet the 20 is test USDC, minted by the escrow program itself (at most 100 per bounty).

Or open a funded issue in one click

What is in escrow for an issue?

Add your own money to someone else's issue (a Solana wallet)

Anyone can add a bounty to any issue of a repo that runs Knos. The same proof pays every bounty on the issue. If nobody is paid by the deadline, yours comes back to your wallet. Devnet USDC comes from Circle's faucet.

How it pays. By default the bounty is paid when a maintainer merges the pull request that closes the issue: the merge is the acceptance, in any language. The payment is held for an hour first, because the pull request's own description says which issue it closes; a maintainer's /knos veto on the issue takes a wrong claim back. /knos bounty 20 review 0 pays at once. To pay without waiting for a merge, put acceptance checks in .knos/acceptance/<issue>/ before funding; they run in a sandbox, and that payment is held for 24 hours. With no proof in 14 days the funder is refunded. Fee: 2.5% (at least 0.05 USDC), only when someone is paid.

Get paid

A Knos bounty is paid to the GitHub account that wrote the pull request. You needed no wallet to do the work. To move the money out, GitHub signs that you asked, from a repository you own.

Claim it with one command

pipx install knos
knos claim YOUR_SOLANA_ADDRESS

It uses your gh login: GitHub signs the claim in a repository you own (you/knos-claim, created with one workflow file if you have none), a relayer carries it to Solana and pays the fee, and the command waits until the money has arrived.

Or in the browser

Then 2: on GitHub, Actions > knos claim > Run workflow, and enter the Solana address that should receive your balance. Nobody else can get GitHub to sign that for your account, and the token can only ever pay that address. You need no SOL: a relayer pays the fee.

Numbers

Counted from the escrow program's own logs on Solana devnet. Knos's own activity is kept apart from outside use, and a funder paying themselves is never counted as either.

Build on it

knos-oidc is a Solana program that verifies a GitHub Actions or GitLab CI token on chain. Any program can then require a fact that GitHub signed: which repository, which commit, which workflow, which account ran it. It has no admin and cannot be upgraded.

Use it from your program

A verified token is an account owned by knos-oidc. Read it; do not call anything. The interface crate has no dependency, so it builds with solana-program, pinocchio or anchor of any version.

knos-oidc-interface = { git = "https://github.com/drexthealpha/Knos", tag = "v0.3.11" }
use knos_oidc_interface::{Token, ISSUER_GITHUB};

let data = token.try_borrow_data()?;
// refuses an account knos-oidc does not own, a token not verified to the end, and a stale one
let tok = Token::read(&token.owner.to_bytes(), &data, now).map_err(|_| ProgramError::InvalidAccountData)?;
if tok.issuer() != ISSUER_GITHUB { return Err(ProgramError::InvalidAccountData); }
let repo = tok.claim_u64("repository_id").ok_or(ProgramError::InvalidArgument)?;
let sha = tok.claim("sha").ok_or(ProgramError::InvalidArgument)?;
// repo and sha are now facts GitHub signed; check the audience and keep your own replay guard

A complete example program with its test: examples/oidc_gate. The crate: crates/knos-oidc-interface. IDLs of both programs: idl/. A JavaScript client with no dependency (an npm tarball on every release): sdk/settle.

What makes it safe to build on

  • The issuers' keys are constants in the binary. A new key enters only on GitHub's own signature, from a workflow whose commit is fixed in the binary. Nobody registers a key by hand.
  • No upgrade authority. Checked live on the Numbers page.
  • The RSA arithmetic is tested against Google's Wycheproof vectors and against OpenSSL on random tokens.
